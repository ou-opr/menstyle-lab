## 一、最重要：17 条断言从未执行，门禁一直是绿的

### 1.1 现象

```
$ node scripts/test-wardrobe.mjs | grep -c '^✓'
45
```

45 一直「对得上」44 个 `check(...)` + 1 行汇总，所以没人怀疑。
但文件里实际写了 **44 个 `check` + 17 个 `acheck` = 61 条断言**。

### 1.2 根因

`scripts/test-wardrobe.mjs` 的 `acheck` 是 fire-and-forget：

```js
const acheck = async (label, fn) => { try { await fn(); ok(label) } catch (e) { bad(...) } }
...
acheck('...', async () => { ... })        // 调用处没有 await
...
process.exit(failed === 0 ? 0 : 1)        // 同步退出，microtask 队列直接丢弃
```

`acheck(...)` 同步执行到第一个 `await` 就返回，后续断言与 `ok()` 都排在 microtask 里；
脚本紧接着的同步 `console.log` + `process.exit()` 在 microtask 出队前就结束了进程。

对照组证明这不是「这种脚本本身不能测异步」：`test-backup.mjs`（11 处）与
`test-backup-v2.mjs`（3 处）的调用处**全部**写了 `await acheck(...)`，它们的异步用例一直在跑。

### 1.3 影响面：正好是整条照片链路

被静默跳过的 17 条断言覆盖 `src/data/imageStore.js` 的全部对外行为：
压缩到 1200 长边、超 900KB 逐级降质量、拒绝非图片、压缩失败降级保存原图、
仓库不可用时 `ok:false`、删除幂等、导出/导入往返、坏记录跳过、挂载失败不留孤儿照片。

覆盖率也帮不上忙：`imageStore` 被 `import` 就会执行模块顶层代码，账本里算「已加载」。

### 1.4 修法（两层）

1. **脚本层**：`acheck` 把 Promise 收进 `pending`，末尾 `await Promise.all(pending)` 再汇总；
   另外打印一行 `本文件执行断言 N 条（其中异步 K 条）`——下次少跑多少条一眼可见。
2. **门禁层**：`scripts/lint.mjs` 新增规则 **`ASYNC-CHECK`**：
   扫 `scripts/*.mjs`，出现 `acheck(` 调用、既没有 `await acheck(` 也没有末尾
   `await Promise.all(...)` 时报错。带 self-test 正反样本（`scripts/bad-async-check.mjs`
   / `scripts/good-async-check.mjs`）。

### 1.5 红/绿对照（真实文件，不是样本）

```
# 把 test-wardrobe.mjs 末尾的 await Promise.all(pending) 删掉
scripts/test-wardrobe.mjs:541:1  ASYNC-CHECK  17 处 acheck(...) 没有 await …   EXIT=1
# 还原
73 个文件, 0 条违规                                                          EXIT=0
```

修复后：`本文件执行断言 61 条（其中异步 17 条）`，17 条首次真正执行，**全部通过**。

## 二、照片压缩：无损格式绕过了 900KB 目标

### 2.1 证据（改前代码）

```js
// src/data/imageStore.js compressBlob()
const blob = await render(bitmap, width, height, type, q)
best = { blob, width, height, type }
if (type !== 'image/jpeg' || blob.size <= TARGET_MAX_BYTES) return best   // ← PNG/WebP 首轮就返回
```

`pickOutputType` 对 PNG/WebP/GIF（或任何带 alpha 的图）返回 `image/png`，
而 PNG 没有质量参数、`toBlob` 忽略 quality，所以**第一轮渲染出来多大就存多大**：
一张信息熵高的手机截图缩到 1200 长边仍可能是 2–4MB，远超 `TARGET_MAX_BYTES = 900KB`。

它和下一节叠加成一条完整的坏链路：图存进 IndexedDB → 导出备份时 dataURL 超 4MB 上限 →
`exportImages` 静默 `continue` → 用户拿到一个「导出成功」但缺照片的备份包。

### 2.2 修法

目标体积对**所有格式**生效：任何格式都走「缩边 × 质量档」，达标才返回；
无损格式只缩边（不做无意义的四档重渲染）；缩到 `MIN_MAX_EDGE = 480` 仍超限、
且原图**没有透明通道**时，转 JPEG 再压一轮（不丢任何视觉信息）。
带透明的图不转 JPEG——宁可保留 PNG 并如实返回最大努力结果。

### 2.3 新增断言（3 条，都在 `test-wardrobe.mjs`）

| 断言 | 说明 |
|---|---|
| PNG 也受 900KB 目标约束 | 断言最终 `type === 'image/jpeg'` 且体积达标；并断言 PNG 阶段确实逐级缩边重试、JPEG 兜底被调用 |
| 透明 PNG 不强转 JPEG | 断言 `type === 'image/png'` 且如实返回超限结果（不丢 alpha、不报错） |
| `exportImages` 的 `onSkip` 上报 | 5MB 照片被跳过时必须回调，不能只打日志 |

**变异测试**（把 `if (blob.size <= …)` 改回 `if (outType !== 'image/jpeg' || …)`）：

```
❌ compressBlob：PNG 也受 900KB 目标约束… — PNG 压不到目标时应在无透明通道的前提下转 JPEG
EXIT=1       还原后：EXIT=0，62 个 ✓
```

## 三、备份导出会静默少照片

### 3.1 证据

`exportImages` 跳过大图时只有 `console.warn`；`exportBackup` 收集不到这件事，
于是返回值里 `warnings` 是空的，`DataManager` 照常显示「导出成功」。

### 3.2 修法

- `exportImages(ids, { store, onSkip })`：跳过时回调 `{ id, reason, size }`
  （三种原因分开：找不到记录 / 无法还原二进制 / 编码后超 4MB 上限）。
- `exportBackup`：收集 skipped，写进 `warnings`——
  「有 N 张照片未写入备份包（单张编码后超过 4MB 上限，建议先在衣橱里重新上传小图）」。
  `DataManager` 本来就会把 `result.warnings` 展示出来，不需要改 UI。
- 新增体积提示：备份包 > 24MB 时追加一条「建议用文件传输而不是聊天窗口发送」，
  返回值同时给出 `bytes`（真实 UTF-8 字节数）。

### 3.3 新增断言（2 条，`test-backup-v2.mjs`）

- 照片被跳过时 `warnings` 必须包含「1 张照片未写入备份包」，且只导出衣橱引用到的 id；
- `bytes === Buffer.byteLength(json)`。

## 六、明确不做的事（以及为什么）

| 不做 | 理由 |
|---|---|
| 拆 `App.jsx`（594 行）/ `garments.jsx`（872 行） | 拆分本身不改变行为，但会动到契约里「Lead 拥有的集成面」，收益是纯审美；当前测试网对 App 层的保护只有 6 条 E2E，大改风险高于收益 |
| 引入 jsdom / testing-library 做组件级覆盖率 | 契约 §0.1 禁止新增依赖；真要提覆盖率应该先改契约，那是产品决策 |
| 首包懒加载 `Sources` | 实测 `sources.js`(85KB) + `link-status.generated.js`(39KB) 占了主包三分之一，但 `AdvicePanel` / `Laws` / `ProfileRecommender` 都要出处数据，拆不开；而且它已经是 `React.memo` |
| 继续压单文件版 3.13MB | 大头是 24 张 PBR webp（约 1.3MB，渲染必需）+ 152KB 字体 + three（685KB，单文件版无法外部化）；再压要牺牲画质 |
| 给全部组件加 `React.memo` | `Sources` / `OutfitCalendar` / `CapsulePlanner` 已 memo；其余组件的 props 每帧都新（outfit/wardrobe），memo 命中率为 0，加了只是噪音 |
| 删除 `test-backup.mjs`（v1 与 v2 并存） | v1 测「13 种损坏包 + 合并/覆盖/回滚」，v2 测 daily/calendar 增量，两者断言不重复；上一轮评审里「建议确认后删除其一」的结论没有证据支撑，删了会丢覆盖 |
| 推送 GitHub | 本地已提交，没推。`git push` 会跑 pre-push 门禁并触发 CI，这是用户该决定的事 |
